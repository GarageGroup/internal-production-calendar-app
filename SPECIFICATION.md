# Спецификация Production Calendar

## Назначение

Два действия: получить конкретный календарный день страны; инициализировать полный календарь страны на указанный год из JSON с overrides. Реальные праздничные даты предоставляет вызывающая сторона. Примеры ниже демонстрируют формат, а не официальный календарь России.

## Модель и хранение

Одна бизнес-таблица `ProductionCalendar`, одна entity на день:

| Поле | Формат | Пример |
| --- | --- | --- |
| PartitionKey | `Country|Year` | `RU|2026` |
| RowKey | `yyyyMMdd` | `20260430` |
| Date | отдельное строковое бизнес-поле `yyyy-MM-dd` | `2026-04-30` |
| DayType | строковое имя enum | `ShortenedDay` |
| Comment | строка | `Предпраздничный день` |

В коде дата — `DateOnly`, тип дня — публичный enum:

```csharp
public enum DayType
{
    WorkingDay,
    Weekend,
    Holiday,
    ShortenedDay
}
```

Entity использует строковое свойство `DayType`; маппинг явный в обе стороны. Не сохранять числовое значение enum. JSON API также отдаёт строковое имя, а не ordinal enum. Для дат и ключей использовать `InvariantCulture`.

| DayType | IsWorkingDay |
| --- | --- |
| WorkingDay | true |
| Weekend | false |
| Holiday | false |
| ShortenedDay | true |

`Country` и `IsWorkingDay` не требуется хранить дополнительными свойствами entity. Country получается из нормализованного входа/ключа, IsWorkingDay вычисляется по enum.

## Получение дня

Вход: Country и Date. Для `RU`, `2026-04-30` выполняется ровно point lookup `RU|2026` / `20260430`. Не сканировать таблицу или partition, не искать ближайшую дату, не подставлять базовый день при отсутствии записи.

```json
{
  "date": "2026-04-30",
  "country": "RU",
  "isWorkingDay": true,
  "dayType": "ShortenedDay",
  "comment": "Предпраздничный день"
}
```

Ожидаемые ошибки: некорректный вход — Invalid; отсутствующая entity — NotFound; сбой Storage или повреждённая entity — Unknown с диагностикой. Проверять, что бизнес-поле Date соответствует ключу и запрошенной дате; неизвестный тип Storage не подменять WorkingDay.

## Инициализация

Вход прикладного метода: Country, Year и JSON. HTTP-адаптер получает Country/Year из маршрута и JSON из тела.

```json
{
  "country": "RU",
  "year": 2026,
  "days": [
    { "date": "2026-01-01", "type": "Holiday", "comment": "Новый год" },
    { "date": "2026-02-21", "type": "WorkingDay", "comment": "Перенос рабочего дня" },
    { "date": "2026-02-23", "type": "Holiday", "comment": "День защитника Отечества" },
    { "date": "2026-04-30", "type": "ShortenedDay", "comment": "Предпраздничный день" }
  ]
}
```

1. Разобрать и проверить весь JSON до любого обращения на запись.
2. Создать дни от 1 января до 31 декабря включительно (365/366), без расчётов через часовые пояса.
3. Понедельник–пятница → WorkingDay; суббота–воскресенье → Weekend; базовый Comment — пустая строка.
4. Применить override соответствующего дня: заменить тип и комментарий.
5. Записать все дни в одну partition посредством replace-upsert.
6. Успех вернуть после подтверждения каждой записи.

Генерация должна работать и для максимального поддерживаемого года, без попытки `AddDays(1)` после `9999-12-31`. Разница между 365 и 366 проверяется календарной арифметикой .NET.

## Правила валидации для реализации

Ниже зафиксированы рабочие решения для случаев, которые исходные требования не уточняют:

- Country: после Trim ровно две ASCII-буквы, нормализация `ToUpperInvariant()`. Это синтаксическая проверка, без справочника поддерживаемых стран.
- Year: 1–9999, формат года в partition всегда четыре цифры.
- Country/Year в JSON обязательны и должны совпасть с параметрами метода после нормализации страны.
- `days` обязателен, `[]` допустим и создаёт базовый календарь. Null вместо массива/элемента — Invalid.
- Date: строгая строка `yyyy-MM-dd`, существующая дата внутри выбранного года.
- Type: только четыре точных имени enum; регистр значим. Числа, числовые строки, неизвестные имена и составные значения отклонять. Одного `Enum.TryParse` недостаточно.
- Одинаковая дата дважды — Invalid, даже если значения совпадают.
- Comment необязателен; отсутствующий/null нормализуется в пустую строку. Непустой комментарий сохраняется без изменений.
- В C#-моделях необязательный Comment имеет тип `string?` без значения по умолчанию. Нормализацию через `.OrEmpty()` выполнять в реализации там, где нужна строка, в частности при записи полного поля Comment в Storage.
- Неправильный JSON, несовпадающие параметры и ошибки выше → Invalid, ноль вызовов записи.

При необходимости изменения этих правил согласовать их при реализации контрактов и обновить документ.

## Идемпотентность и ограничения записи

Каждая инициализация формирует новый полный год на базе текущего JSON. Фиксированные ключи исключают дубли; HTTP PUT insert-or-replace перезаписывает business-поля целиком. Режим merge не использовать: исчезнувший комментарий должен очищаться.

Пример: первая инициализация назначает `2026-04-30` Holiday с комментарием. Вторая инициализация с `days: []` возвращает этот четверг к WorkingDay с пустым комментарием. Другие страны и годы не затрагиваются.

Первая реализация может записывать дни последовательно через point upsert, как в образце. Атомарная запись всего года не обещается: при сбое возможен частично обновлённый год, повтор полной инициализации восстанавливает результат. Не возвращать успех при частичной записи. Конкурирующие инициализации одной partition пока не сериализуются: выполнять их последовательно на стороне вызывающего процесса. Блокировки, batch и версии календаря — отдельное расширение при необходимости.

## Предварительный HTTP-контракт

На этапе HTTP закрепить маршруты и схемы тестами:

- `GET /api/production-calendar/{country}/{date}` → 200 с моделью дня; 400 Invalid; 404 NotFound; 500 Unknown.
- `POST /api/production-calendar/{country}/{year}/initialize` → JSON overrides в теле; 200 с Country, Year, DaysCount после полной записи; 400 Invalid; 500 Unknown.
- `AuthorizationLevel.Function`, как у HTTP endpoints образца; JSON свойства ответа camelCase, DayType строкой.
- Ошибки в стиле образца: `{ "error": "..." }`; не включать секреты и подробности инфраструктурных исключений в HTTP-ответ.

Маршруты и ответ инициализации — предложенные решения, а не уже реализованный API.

Даты указываются по Europe/Moscow. Журнал фиксирует выполненные изменения и решения; актуальные правила находятся в AGENTS.md, ARCHITECTURE.md и SPECIFICATION.md. Одобрение и коммит отмечаются только после соответствующего события.

## 2026-10-06 — Инкремент 0: исследование и каркас

**Выполнено:** изучены структура и код-стиль internal-exchange-rates-app, AsyncPipeline, Dependency, Storage REST, Azure Functions, Bicep и workflows. Созданы solution и девять проектов .NET 10, ссылки между проектами, каталоги с .gitkeep, инструкции, архитектура, спецификация и план реализации/CI/CD.

**Требования пользователя:** повторить подходы и дерево образца, применять AsyncPipeline и такой же Dependency; начать с пустых проектов и подробного плана; CI/CD реализовать после приложения.

**Самостоятельно принятые решения:**

- Девять проектов для двух действий вместо тринадцати в образце; сохранить слои app/endpoint/service и разделение Contract/Api/Handler.
- Чистый сервис ProductionCalendar заменяет сервис внешнего поставщика курсов; он не зависит от HTTP или Azure. Общий enum размещается в его Contract.
- AzureFunc временно Library для сборки пустого проекта; переключить на Exe вместе с Program.cs на этапе хоста.
- Сохранить версии и настройки пакетов образца. Не вводить центральные props или новый DI-стек.
- Инициализация строит и replace-upsert записывает весь год, чтобы удалённые overrides и комментарии сбрасывались. В первой реализации последовательные записи; атомарность года и сериализация конкурирующих инициализаций не предусмотрены.
- Рабочие правила валидации: Country — две ASCII-буквы после Trim/uppercase; Year — 1–9999; обязательные country/year/days в JSON; точные имена type; строгие даты внутри года; повтор дат запрещён; отсутствующий/null Comment становится пустым. Эти уточнения записаны в SPECIFICATION.md, отдельного одобрения пользователя для каждого правила не было.
- Маршруты GET дня и POST initialize, ответ инициализации Country/Year/DaysCount записаны как предварительные предложения до этапа HTTP.
- Не переносить бизнес-таймеры и Dataverse-конфигурацию образца: текущие требования календаря их не используют. Подходы Flex Consumption, OIDC, Managed Identity, Test/Prod и lifecycle ZIP сохранить для CI/CD.

**Проверки:** SDK 10.0.401; restore и Release build всех девяти проектов успешны, 0 ошибок/предупреждений. Бизнес-тестов на этапе каркаса нет.

**Статус:** каркас завершён; история/одобрение его коммита в рамках выполненных действий не фиксировались. Следующий этап — контракты.

## 2026-10-06 — Инкремент 1: контракты и бизнес-модель

**Выполнено:** добавлены 23 C#-файла: DayType, DayTypeExtensions, ProductionCalendarDay; контракты построения полного года, получения/записи дня в Storage и получения/инициализации календаря через endpoints. Добавлены supplier/handler-интерфейсы и failure codes; удалены .gitkeep заполненных каталогов. Обновлены архитектура и чекбоксы плана.

**Решение пользователя о процессе:** после каждого инкремента остановка для ревью без коммита; после одобрения или «продолжай» — коммит и следующий инкремент.

**Самостоятельно принятые решения:**

- Сохранить стиль DTO образца: входы чтения, построения и инициализации — readonly record struct; модели, outputs и storage set input — sealed record class.
- IsWorkingDay вычисляется через общий DayTypeExtensions, без независимо задаваемого флага. WorkingDay/ShortenedDay дают true, Weekend/Holiday — false; неизвестный enum вызывает ArgumentOutOfRangeException. Валидация входа/Storage будет добавлена в последующих этапах.
- Вход построения и инициализации содержит строковое Json; JSON DTO остаются внутренними для будущей реализации.
- Полный календарь возвращается в FlatArray<ProductionCalendarDay>; добавить прямую ссылку PrimeFuncPack.Core.FlatArray 1.5.1, совпадающую с зависимостью update-handler образца.
- Асинхронные контракты используют ValueTask<Result<T, Failure<TCode>>> и CancellationToken. SetDayAsync возвращает Unit. Failure codes: Unknown/Invalid; дополнительно NotFound для Storage и чтения дня.
- Контракт инициализации использует прямые Failure/Result вместо пакета Handler.Core, который в образце обслуживает timer-handler.
- Country/Json — required; Date/Year — DateOnly/int; первоначально Comment имел пустой строковый initializer (заменён на nullable по замечанию пользователя ниже). Runtime-валидация и строковая транспортная сериализация enum относятся к следующим этапам.



**Проверки:** после добавления прямой зависимости FlatArray выполнены успешные restore и Release build всего решения: 0 ошибок/предупреждений. git diff --check не выявил ошибок пробелов. Тесты поведения на этом этапе не добавлялись.

**Статус:** реализация готова к ревью; пользователь пока не одобрил инкремент. Коммит не выполнен. Следующий шаг после одобрения — коммит инкремента 1 и этап 2, построение календаря с тестами.

## 2026-10-06 — Исправления ревью инкремента 1: nullable и сравнения

**Решение пользователя:** обязательные поля — required, необязательные — nullable без `= string.Empty;`; если реализации нужна строка, применять OrEmpty. Не использовать null-forgiving `!`; предпочитать is/is not при сравнениях.

**Выполнено:** Comment заменён на `string?` без инициализатора в ProductionCalendarDay, StorageGetOut, StorageSetIn и endpoint GetOut. Обновлены AGENTS.md, ARCHITECTURE.md, SPECIFICATION.md, IMPLEMENTATION_PLAN.md и PROJECT_GUIDE.md. Исправление относится к текущему инкременту 1.

**Уточнение применения:** is/is not использовать для null, bool и других constant patterns; для сравнения двух переменных — соответствующие Equals/методы. Нормализация nullable Comment будет реализована в последующих слоях, в частности для replace-upsert Storage.

**Проверки:** Release build всего решения успешен: 0 ошибок, 0 предупреждений. В текущих исходниках нет string.Empty, null-forgiving или операторов ==/!=; все четыре Comment — nullable.

**Статус:** сообщение «продолжай» отозвано последующим «стоп». Коммит не выполнялся, инкремент 2 не начинался; исправленный инкремент 1 ожидает повторного ревью.
